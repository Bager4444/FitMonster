# План: облачная синхронизация (Firebase Firestore)

Цель: данные пользователя доступны с **любого устройства**, доступ к документам только у **вошедшего владельца** (Firebase Auth + Security Rules). Бесплатный старт — тариф **Spark** в одном проекте Firebase.

---

## Пошагово: что сделать в Firebase Console

Интерфейс консоли на английском; ниже указаны **точные подписи кнопок и вкладок**.

### Шаг 1 — Войти и открыть нужный проект

1. Откройте в браузере: **https://console.firebase.google.com/**
2. Войдите в аккаунт Google, которым управляете проектом.
3. На главной нажмите на проект **`fitmonster-ede5c`** — он должен совпадать с **`project_id`** в `android/app/google-services.json`.  
   - Если такого проекта нет — сначала создайте проект (**Add project** / **Создать проект**), затем добавьте Android-приложение и заново скачайте `google-services.json` (это уже отдельная настройка; у вас проект уже привязан к приложению).

### Шаг 2 — Включить вход по почте и паролю (Email/Password)

1. В **левом меню** откройте **Build** → **Authentication**.
2. Если видите кнопку **Get started** — нажмите её.
3. Откройте вкладку **Sign-in method** (способ входа).
4. В списке провайдеров найдите строку **Email/Password**.
5. Нажмите на **Email/Password**.
6. Переключатель **Enable** поставьте в **On** (включено).
7. **Email link (passwordless sign-in)** для MVP можно оставить **выключенным**.
8. Нажмите **Save**.

Ничего больше в этом окне писать не нужно — только включить провайдер.

### Шаг 3 — Создать базу Firestore (если ещё не создана)

1. В **левом меню**: **Build** → **Firestore Database**.
2. Если базы ещё нет, нажмите **Create database**.
3. Выберите **Start in production mode** → **Next**.  
   (Временные правила «закрыть всё» нас не устраивают надолго — их заменим на шаге 4.)
4. Выберите **регион** (например **europe-west3** или **europe-west1**) → **Enable** / **Готово**.
5. Дождитесь окончания создания.

Если база **уже создана**, подпункты **2–5** этого шага не делаете — сразу переходите к **шагу 4** (вкладка **Rules**).

### Шаг 4 — Вставить правила безопасности (Security Rules)

1. Оставаясь в **Firestore Database**, откройте вкладку **Rules**.
2. **Полностью замените** содержимое редактора на текст ниже (скопируйте целиком).
3. Нажмите **Publish**.

**Текст для вставки в Rules (скопировать от `rules_version` до последней `}`):**

```rules
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}
```

После **Publish** консоль может показать предупреждения — для разработки это нормально; позже правила можно ужесточить.

### Шаг 5 — Проверить, что Android-приложение привязано к проекту

1. Слева внизу нажмите **шестерёнку** → **Project settings** (Настройки проекта).
2. Вкладка **General** → блок **Your apps**.
3. Должно быть приложение **Android** с package name **`com.fitmonster.app`**.  
   Если его нет — **Add app** → Android → укажите package `com.fitmonster.app`, скачайте новый `google-services.json` и положите в `android/app/` (как в документации FlutterFire).

**Ничего вручную «генерировать» для Firestore не нужно:** приложение уже использует данные из `google-services.json`.

### Шаг 6 — Биллинг (платить не обязательно)

1. В **Project settings** → вкладка **Usage and billing** (или **Spark** в шапке).
2. Убедитесь, что план **Spark** (бесплатный). Платный **Blaze** не включайте, если не планируете платные квоты.

**На этом настройка консоли для Android завершена.** Шаг 7 можно не делать.

### Шаг 7 — iOS (необязательно; пропускайте, если только Android)

1. **Project settings** → **Your apps** → **Add app** → **iOS**.
2. Укажите Bundle ID из Xcode → скачайте **GoogleService-Info.plist** → добавьте в проект Flutter по инструкции Firebase.

Без шага 7 приложение на **Android** и **Windows/Web** (если настроите) от Firestore/Auth не страдает.

### Что в консоли писать руками не нужно

- Отдельный «секретный ключ API» для записи в Firestore **не создаёте** — доступ даёт Firebase SDK + Auth + Rules.
- Сервисный аккаунт (**Service accounts**) для мобильного приложения **не качаете**; он нужен только для серверного кода (Functions, Admin SDK), не для телефона.

### FAQ: в Authentication есть пользователь, в Firestore — пусто

1. **Это разные системы.** Список в **Authentication → Users** не создаёт строки в **Firestore → Data** сам по себе. В облаке появляется документ только когда **приложение** (с вошедшим Firebase-пользователем) выполняет **запись** (у нас — `users/{uid}/sync/account`).

2. **Одна база на проект.** Не существует отдельной «новой базы на каждого юзера». У проекта одна Firestore; пользователи различаются **путём документа** (`users/<их uid>/...`).

3. **Что сделать, чтобы запись появилась**
   - Убедиться, что **Firestore Database** создана (**Build → Firestore Database**), а **Rules** не `allow read, write: if false`, а правила с `users/{userId}` и `request.auth.uid == userId`.
   - На устройстве открыть приложение → **Профиль** → **войти** тем же email/паролем, что в Authentication (или зарегистрироваться из приложения).
   - После успешного входа в консоли **Firestore → Data** должны появиться: коллекция **`users`** → документ с **UID** (как в Authentication, без префикса `firebase_`) → **`sync`** → **`account`**.
   - Во время отладки смотрите лог Flutter: строки `UserAccountFirestoreSync: запись OK` или текст ошибки / «пропуск Firestore — не вызван attachFirestorePush».

4. **Пользователь только добавлен вручную в консоли** — пока вы **ни разу не вошли в приложение** этой учёткой, в Firestore документов не будет.

## 2. Принципы синхронизации

1. **Источник истины при конфликте (MVP):** `updatedAt` (или серверный timestamp) — более новая запись побеждает; при равенстве — приоритет локальной или серверной (зафиксировать в коде один раз).
2. **Офлайн:** Firestore SDK кэширует данные; Hive остаётся для быстрого старта и полного офлайна без сети — при появлении сети **push/pull** по очереди.
3. **Гость (`user_xxx` без Firebase):** облако **не привязываем** по правилам безопасно. Варианты: (a) синк только для `isEmailUser`; (b) экран «Войти, чтобы синхронизировать»; (c) опциональная миграция гостя → привязка к новому Firebase-аккаунту (отдельный сценарий).
4. **Секреты:** **`passwordHash` и любые токены в Firestore не пишем.** Пароль живёт только локально / в Firebase Auth на стороне Google.

## 3. Модель данных Firestore (черновик)

Корень: **`users/{firebaseUid}`** — `firebaseUid` **без** префикса `firebase_` в пути (в коде: `uid = userId.replaceFirst('firebase_', '')`).

Рекомендуемая структура (итерация 1):

**Реализовано (MVP):**
- `users/{firebaseUid}/sync/account` — `UserAccount` без `passwordHash` (как `toMap`).
- `users/{firebaseUid}/sync/metrics` — **ударный режим** (`isStreakModeEnabled`), стрик дней, тренировки, калории за неделю, веса, XP/уровень, имя в UI, список `achievementIds`.
- `users/{firebaseUid}/sync/diet_profile` — профиль питания (`UserProfile.toMap()`), если `userId` совпадает с аккаунтом.

```
users/{uid}/
  sync/account     — ✅ UserAccount (без passwordHash), merge при записи
  sync/metrics     — ✅ показатели профиля/статистики (см. выше)
  sync/diet_profile — ✅ антропометрия и цели питания (если профиль сохранён)
  profile          — документ: UserProfile / питание (как toMap из модели, без секретов)
  account          — (план) дублировать имя «account» не требуется — используется sync/account
  app_profile      — документ: AppProfile (если отдельно от profile)
  meta             — lastFullSyncAt, schemaVersion

users/{uid}/food_logs/{logId}     — записи дневника (или один документ с массивом — оценить размер)
users/{uid}/workouts/{sessionId}  — сессии тренировок
users/{uid}/settings/{key}      — опционально, или один документ settings
```

**Не синкать или отдельно:** глобальная база продуктов `foods` (уже из JSON локально) — при необходимости позже общая коллекция только для пользовательских кастомных продуктов.

**AI-чат:** либо подколлекция `users/{uid}/ai_messages/{id}`, либо оставить только локально в MVP.

## 7. Риски и неопределённости

- **Объём документов:** большие массивы логов — разбивка по подколлекциям / пагинация.
- **Миграция гостя → Firebase:** перенос Hive-ключей и слияние с облаком — отдельное ТЗ.
- **Ранги (world/region):** если станут серверными — не перезаписывать с клиента без Cloud Function.
