# Техническое задание (ТЗ)
## Модуль управления задачами в FitMonster

## 1. Цель и результат
- Добавить в приложение полноценный менеджер задач.
- Пользователь должен иметь возможность:
  - создавать и редактировать задачи;
  - отмечать задачи выполненными;
  - удалять выполненные задачи (по одной и массово);
  - задавать приоритет;
  - задавать дедлайн;
  - заполнять подробное описание задачи.

Результат внедрения: пользователь управляет личным планом действий внутри приложения (тренировки, питание, привычки) в одном месте без внешних трекеров.

## 2. Область реализации
- Платформы: Android, iOS.
- Локальное хранение: Hive.
- Синхронизация с облаком: опционально, через существующий слой данных (если уже реализован для профиля).
- Язык интерфейса: русский.

## 3. Термины
- Задача — карточка действия с полями: название, описание, приоритет, дедлайн, статус.
- Выполненная задача — задача со статусом `done`.
- Просроченная задача — задача со статусом `todo/in_progress`, у которой дедлайн меньше текущего времени.
- Приоритет — уровень важности: `low`, `medium`, `high`, `critical`.

## 4. Функциональные требования

### FR-1. Создание задачи
Пользователь может создать задачу с обязательными и необязательными полями.

Обязательные поля:
- Название (1-120 символов).
- Приоритет (по умолчанию `medium`).

Необязательные поля:
- Подробное описание (до 5000 символов).
- Дедлайн (дата и время).

Критерии приемки:
- Нельзя сохранить пустое название.
- После сохранения задача появляется в списке без перезагрузки экрана.

### FR-2. Редактирование задачи
Пользователь может изменить любое поле задачи, включая описание, дедлайн и приоритет.

Критерии приемки:
- Изменения сохраняются локально сразу после подтверждения.
- Дата обновления (`updatedAt`) перезаписывается.

### FR-3. Статус выполнения
Пользователь может:
- отметить задачу как выполненную;
- вернуть выполненную задачу в активные.

Критерии приемки:
- При отметке выполнения проставляется `completedAt`.
- Выполненные задачи визуально отличаются от активных.

### FR-4. Удаление выполненных задач
Пользователь может удалять:
- одну выполненную задачу;
- все выполненные задачи массовым действием.

Критерии приемки:
- Для удаления показывается подтверждение действия.
- Массовое удаление удаляет только задачи со статусом `done`.
- Активные и просроченные задачи при массовом удалении не удаляются.

### FR-5. Приоритеты
Для каждой задачи задается приоритет:
- `low` — низкий;
- `medium` — средний;
- `high` — высокий;
- `critical` — критический.

Критерии приемки:
- Список задач сортируется по приоритету и дедлайну (настраиваемо).
- Приоритет отображается цветовым индикатором и текстом.
- Цвета корректно отображаются в светлой и темной темах.

### FR-6. Дедлайн
Пользователь может задать дату и время дедлайна.

Критерии приемки:
- Дедлайн не обязателен.
- Для просроченных задач отображается статус "Просрочено".
- Фильтр "Сегодня", "7 дней", "Просроченные" работает корректно.

### FR-7. Подробное описание и чек-лист выполнения
В задаче должен быть блок "Описание" с инструкцией "как и что делать".

Поддержка в описании:
- многострочный текст;
- простые чек-боксы в формате списка;
- переносы строк и сохранение структуры текста.

Критерии приемки:
- Описание отображается полностью на экране деталей.
- В списке задач показывается укороченный превью-фрагмент (до 2 строк).

## 5. Экранный состав (UI)

### 5.1 Экран списка задач
Содержит:
- поиск;
- фильтры по статусу (все, активные, выполненные, просроченные);
- фильтры по приоритету;
- сортировку (по дедлайну, по приоритету, по дате создания);
- кнопку "Удалить выполненные".

### 5.2 Экран создания/редактирования задачи
Поля формы:
- название;
- описание (подробное);
- приоритет (селектор);
- дедлайн (date-time picker);
- статус.

Кнопки:
- "Сохранить";
- "Отмена";
- "Удалить" (только в режиме редактирования).

### 5.3 Экран деталей задачи
Показывает полную информацию:
- название;
- статус;
- приоритет;
- дедлайн;
- подробное описание;
- даты создания/обновления/выполнения;
- действия: "Редактировать", "Отметить выполненной", "Удалить".

## 6. Модель данных

Сущность `Task`:
- `id: String` (UUID)
- `title: String`
- `description: String?`
- `priority: TaskPriority` (`low|medium|high|critical`)
- `status: TaskStatus` (`todo|in_progress|done`)
- `deadlineAt: DateTime?`
- `createdAt: DateTime`
- `updatedAt: DateTime`
- `completedAt: DateTime?`

Индексы/оптимизация выборки:
- по `status`;
- по `deadlineAt`;
- по `priority`.

## 7. Бизнес-правила
- Нельзя создавать задачу без названия.
- При переводе задачи в `done`:
  - выставляется `completedAt`;
  - задача попадает в группу выполненных.
- При возврате из `done` в активные:
  - `completedAt = null`.
- Массовое удаление работает только для `done`.
- Если дедлайн уже прошел и задача не `done`, задача считается просроченной автоматически.

## 8. Нефункциональные требования
- Время отклика UI для операций списка: до 150 мс на выборках до 1000 задач.
- Оффлайн-режим: 100% для операций CRUD.
- Устойчивость: после перезапуска приложения данные задач сохраняются.
- Доступность: читаемость текстов и контраст в светлой/темной теме.
- Безопасность: данные хранятся локально в изолированном контейнере приложения.

## 9. Подробный план реализации (как и что делать)

### Этап 1. Подготовка слоя данных
1. Создать модель `Task` и enum'ы `TaskPriority`, `TaskStatus`.
2. Добавить сериализацию/десериализацию для Hive.
3. Создать репозиторий задач:
   - `createTask`
   - `updateTask`
   - `deleteTask`
   - `deleteCompletedTasks`
   - `watchTasks`/`getTasks`
4. Покрыть слой данных unit-тестами.

Ожидаемый результат:
- Стабильный CRUD и массовое удаление выполненных задач.

### Этап 2. State management
1. Добавить provider/notifier для задач.
2. Реализовать состояние:
   - список задач;
   - активные фильтры;
   - сортировка;
   - загрузка/ошибки.
3. Реализовать методы:
   - `toggleDone`
   - `setPriority`
   - `setDeadline`
   - `applyFilter`
   - `deleteCompleted`.

Ожидаемый результат:
- UI получает реактивное состояние и обновляется без ручной перезагрузки.

### Этап 3. UI-экраны
1. Экран списка задач с фильтрами/сортировкой.
2. Экран формы создания/редактирования.
3. Экран деталей задачи с полным описанием.
4. Подтверждение удаления (single и bulk).

Ожидаемый результат:
- Полный пользовательский поток от создания до удаления выполненной задачи.

### Этап 4. Валидация и UX-детали
1. Валидация заголовка, лимитов длины, корректности даты.
2. Визуальные статусы: выполнено/просрочено/приоритет.
3. Поддержка светлой и темной темы для всех индикаторов.

Ожидаемый результат:
- Предсказуемое поведение и понятные пользователю ошибки.

### Этап 5. Тестирование
1. Unit-тесты: бизнес-правила и репозиторий.
2. Widget-тесты: форма задачи, фильтры, сортировка.
3. Интеграционные сценарии:
   - создание задачи с дедлайном и высоким приоритетом;
   - завершение задачи;
   - удаление одной выполненной;
   - массовое удаление выполненных;
   - проверка просроченных задач.

Ожидаемый результат:
- Регрессии по основным сценариям отсутствуют.

## 10. Критерии готовности (Definition of Done)
- Все требования FR-1...FR-7 реализованы.
- Реализованы удаление выполненных задач и массовое удаление.
- Работают приоритеты, дедлайны и подробное описание.
- Тесты на ключевые сценарии проходят.
- UI корректен в светлой и темной темах.
- Документация обновлена и согласована.

## 11. Ограничения и допущения
- Уведомления о дедлайнах не входят в текущий объем (могут быть отдельной задачей).
- Синхронизация между устройствами не обязательна для первой версии модуля.
- ТЗ описывает MVP модуля задач; расширения оформляются отдельными изменениями.
